## Requirement

Prevent a repeated `POST /api/orders` submission from creating another order when the client retries after an uncertain network result.

## Behaviour

- Clients may send an `Idempotency-Key` header with an order request.
- The key is unique per student. Reusing the same key for that student returns the original order with HTTP 200 and does not create another order.
- A new keyed order returns HTTP 201. Requests without a key retain the existing create behavior.
- A unique MongoDB index prevents two simultaneous submissions from creating two orders with the same student/key pair. If a simultaneous request loses the race, the API returns the winning order.
- The checkout form retains the key after a failed request for the same request body, and uses a new key after a successful order or when the request body changes.

## Automated verification

Run from `backend/`:

```bash
npm test
```

`tests/order-idempotency.test.js` checks the index definition, repeated submission behavior, and the duplicate-key race. The route tests use mocked model operations and do not require a live MongoDB instance.

| Check | Actual result |
|---|---|
| First request with a key | HTTP 201; one order created — pass |
| Same student submits the same key again | HTTP 200; same order ID; no additional create or menu lookup — pass |
| Two simultaneous requests use the same key | One stored order; one response is HTTP 201 and the other HTTP 200 — pass |
| MongoDB index definition | Unique on `studentId` + `idempotencyKey`, partial for string keys — pass |

The route tests mock persistence, so they verify duplicate-key handling and response behavior without confirming index creation against a running MongoDB server.
