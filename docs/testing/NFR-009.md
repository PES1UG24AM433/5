## Dataset and load

The script refused to run unless the test database was empty, then seeded the same authenticated synthetic student with the baseline and increased dataset. The baseline was measured first; additional records were inserted for the increased-data measurement.

| Stage | Menu items in database | Orders for test student |
|---|---:|---:|
| Baseline | 3 | 50 |
| Increased | 1,000 | 5,000 |

Each stage sent 30 requests to `GET /api/menu` and 30 to authenticated `GET /api/orders`, with concurrency 5 per endpoint. Both endpoints were warmed with 5 requests before measurements. The order response includes all orders belonging to the authenticated student.

## Results

Latency values are milliseconds. Response size is the mean bytes downloaded per request.

| Stage | Endpoint | p50 | p90 | Max | Requests/s | Mean response bytes | Failures |
|---|---|---:|---:|---:|---:|---:|---:|
| Baseline | `GET /api/menu` | 41.07 | 94.03 | 124.23 | 87.26 | 390 | 0 |
| Increased | `GET /api/menu` | 109.08 | 138.95 | 152.19 | 42.52 | 122,576 | 0 |
| Baseline | `GET /api/orders` | 49.32 | 75.84 | 82.86 | 91.79 | 12,677 | 0 |
| Increased | `GET /api/orders` | 1,032.87 | 1,166.47 | 1,230.38 | 4.77 | 1,275,020 | 0 |

The backend Node process RSS was sampled every 100 ms: baseline-stage sample 115.10 MiB, increased-stage sample 227.71 MiB, and maximum observed sample 237.34 MiB. No request errors or non-2xx responses occurred. CPS-NF-009 specifies no numeric limit, so for context these results are compared with the CPS-NF-001 target of at least 90% of menu and order API requests completing within 3 seconds. The increased-data p90 values (139 ms for menu and 1,166 ms for orders) are within that target at the tested sizes. This comparison is indicative because each stage had only 30 measured requests; it does not establish a general capacity limit.

## Bottleneck

MongoDB `executionStats` for the order-history query showed:

| Stage | Execution time | Documents examined | Index keys examined | Plan |
|---|---:|---:|---:|---|
| Baseline (50 orders) | 1 ms | 50 | 0 | `COLLSCAN`, `SORT` |
| Increased (5,000 orders) | 25 ms | 5,000 | 0 | `COLLSCAN`, `SORT` |

The order-history query itself took 25 ms (`COLLSCAN` + `SORT`), while the endpoint p50 was about 1.03 seconds. Most endpoint latency therefore comes from loading, serializing, and transferring all 5,000 matching orders (about 1.28 MB), rather than the measured scan and sort. Pagination is the primary follow-up improvement to limit response work and payload size. A `studentId` + `orderTime` compound index is a secondary improvement to avoid scanning and sorting all matching records.

`GET /api/menu` also returns every menu item without pagination. At 1,000 items its average response was about 123 KB and p90 increased from 94 ms to 139 ms, so this is a smaller but growing payload risk at the tested size. Menu pagination or bounded results may be appropriate as the catalog grows.

## Limitations and cleanup

- This is a local single-host test; it does not model production network latency, concurrent users with different data, or production hardware.
- Only one run per dataset and 30 measured requests per endpoint were used. Results are indicative and may vary with cache state and machine load.
- With only 30 samples, p99 would be effectively the maximum observation and is omitted rather than treated as a meaningful tail-latency estimate.
- All 5,000 increased-dataset orders belong to one synthetic student, an extreme order-history case. A staff queue or reporting view that reads orders across many students would be a more realistic scalability risk and was not measured here.
- RSS measures the backend Node process, not MongoDB memory; CPU profiling was not performed.
- The result covers the explicit dataset sizes above only.
- The test data was deleted after the run. MongoDB counts for `menuitems` and `orders` in the test database were confirmed to be zero.

## Reproduction

From `backend/`:

```bash
CPS_TEST_MONGODB_URI=mongodb://127.0.0.1:27017/canteen_preorder_test \
  node scripts/scalability-benchmark.js
```

The script only accepts a local MongoDB server and the exact `canteen_preorder_test` database. It refuses to run if that database already contains menu items or orders, starts a separate backend process on an available local port, and removes only the records it created.
