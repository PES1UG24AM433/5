# CPS-NF-001 — API Response Time

| | |
|---|---|
| **GitHub issue** | #21 |
| **Test case** | TC-PERF-01 |
| **Test date** | 30 Oct 2026 |
| **Tool** | autocannon 8.0.0 |
| **Result** | **Pass** |

## Acceptance criterion

At least 90% of menu and order API requests respond within 3 seconds under normal academic/demo load.

## Environment

- Fedora Linux 44, GNOME 50
- Node.js 20.11.0, npm 10.2.4
- Local MongoDB 7.0.45 (database `canteen_preorder`), on the same machine as the backend
- Backend: `http://localhost:5000`
- Authenticated requests used a test student's JWT (not recorded here)

## Test data

Three sample menu items were added to the local test database:

| Item | Price | Type | Stock |
|---|---:|---|---:|
| Test Veg Wrap | 5 | Veg | 20 |
| Test Pasta | 8 | Veg | 15 |
| Test Chicken Bowl | 10 | Non-Veg | 10 |

```js
use canteen_preorder

  { name: "Test Chicken Bowl", price: 10, foodType: "Non-Veg", available: true, stock: 10 }
```

The existing order count/data volume was not recorded. The order-creation test created 50 test orders.

## Test load

| Endpoint | Method | Concurrency | Duration / count |
|---|---|---:|---|
| `/api/menu` | GET | 10 connections | 30 s |
| `/api/orders` (authenticated) | GET | 10 connections | 30 s |
| `/api/orders` (authenticated) | POST | 5 connections | 50 requests |

## Commands

```bash
# Menu
npx autocannon -c 10 -d 30 -j http://localhost:5000/api/menu

# Order retrieval (authenticated)
read -rsp "Test student JWT: " TOKEN; echo
npx autocannon -c 10 -d 30 -j \
  -H "Authorization=Bearer $TOKEN" \
  http://localhost:5000/api/orders
unset TOKEN

# Order creation (authenticated)
read -rsp "Test student JWT: " TOKEN; echo
npx autocannon -c 5 -a 50 -m POST \
  -H "Authorization=Bearer $TOKEN" \
  -H "Content-Type=application/json" \
  -b '{"items":[{"productId":"6ae4fedb1ce5e1b5d7b690fd","quantity":1}]}' \
  http://localhost:5000/api/orders
unset TOKEN
```

## Results

All latencies are in milliseconds.

| Endpoint | Requests | Avg | p50 | p90 | p97.5 | p99 | Max | Errors / timeouts / non-2xx |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| `GET /api/menu` | 12,926 | 22.68 | 21 | **31** | 41 | 49 | 101 | 0 / 0 / 0 |
| `GET /api/orders` | 5,330 | 55.74 | 50 | **79** | 112 | 136 | 305 | 0 / 0 / 0 |
| `POST /api/orders` | 50 | 58.86 | 55 | ≤ 116* | 116 | 126 | 126 | none reported |

\* The order-creation run was not captured with `-j`, so p90 was not reported. It is bounded by the reported p97.5 value (116 ms).

For all three endpoints, p90 is well below the 3,000 ms threshold (largest 79 ms measured, or at most 116 ms), so the criterion is met.

## Notes

- The order-creation request body must use `productId`. A first attempt using `menuItemId` was rejected with HTTP 400 ("Please correct the order details"), so no orders were created from it.
- Only the final successful runs are kept as evidence.

## Limitations

- Measured on a local machine with the database on the same host, so network latency and production hosting are not included.
- Only three menu items were in the database, so these results do not show behaviour at larger data sizes. That is tested separately under CPS-NF-009.
- number of products in stock not decreasing when put to cart and ordered
